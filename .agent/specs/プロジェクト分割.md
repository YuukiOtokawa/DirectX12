## 目的と対象範囲

### 目的

1. **スクリプトのホットリロードの反復時間を短くできる構成にする**。スクリプトを1行変えてからエディタに反映されるまでの時間は、スクリプトが引き込むヘッダの量（コンパイル）と、エンジンをどうリンクするか（リンク）で決まる。どちらも分割の設計で決まってしまう。
2. **製品ビルドからエディタのコードを `#ifdef` なしで除く**。「Editor プロジェクトに入っているファイルは製品ビルドに存在しない」という形で解決する（TODO「デプロイ機能」への布石）。
3. **Core から Editor への依存が無いことをリンカで検証できるようにする**。ImGui をリンクしない `AsteroidPlayer.exe` がビルドできれば、それが証明になる。

## 公開API・編集項目

### Inspector の分離（Unity の CustomEditor 方式）

Core 側の変更:

- `Object::DrawInspector()`、`Component::Inspector()` / `DrawInspector()`、`GameObject::DrawInspector()` を削除する。
- 各コンポーネントから `Inspector()` の実装と `imgui.h` の include を取り除き、Drawer が必要とするアクセサを公開する。
- `Component` に `virtual const char* GetTypeName() const` を追加する。`REGISTER_COMPONENT` が持っている `#Type`（今は private の `GetClassName()`）を公開するもの。`ComponentFactory` の登録キーと一致するので、シリアライズでもそのまま使える。`typeid().name()` は MSVC 依存の名前になるので使わない。

Editor 側の新設:

```cpp
namespace EditorUI {
    using ComponentDrawer = std::function<void(EngineCore::General::Component&)>;

    class InspectorRegistry {
    public:
        static InspectorRegistry& Get();
        void Register(const std::string& typeName, ComponentDrawer drawer);
        // 型名を見出しに描き、登録が無い型は「No custom inspector」とだけ描く
        void Draw(EngineCore::General::Component& component);
        // 指定した型名の Drawer だけを描く（派生の Drawer から基底の Drawer を呼ぶ用）
        bool DrawAs(const std::string& typeName, EngineCore::General::Component& component);
    };
}

#define REGISTER_INSPECTOR(Type, Fn) \
    static const bool s_InspectorRegistered_##Type = [] { \
        ::EditorUI::InspectorRegistry::Get().Register(#Type, Fn); return true; }();
```

- `InspectorWindowController` は、GameObject の名前・Active・コンポーネント一覧・Add Component ポップアップを自分で描き、コンポーネントごとに `InspectorRegistry::Get().Draw(*component)` を呼ぶ。
- UI の編集途中の状態（`PostProcessComponent` の `m_NewName[256]` / `m_NewShaderPath[256]` など）は Drawer 側に移す。製品ビルドからも消える。
- **実装済み（Phase 1）**: 上記のとおり `Editor/Inspector/InspectorRegistry.*` と7本の Drawer を作った。計画からの変更点は次のとおり。
  - `DrawAs()` を追加した。`FractalTreeRenderer` の Drawer が、基底の `MeshRenderer` の Drawer を呼ぶために使う。
  - Inspector の見出しは、従来どのコンポーネントでも「Component」になっていた（静的関数 `GetClassName()` を基底クラスから呼んでいたため）。`GetTypeName()` によって実際の型名が出るようになった。
  - `GameObject` に `AddComponent(std::unique_ptr<Component>)` を追加した。Add Component ポップアップで、型名から生成したコンポーネントを追加するのに使う。
  - `Object::DrawInspector()` を削除すると `Object` が多態型でなくなるので、代わりに virtual デストラクタを追加した。
  - `PostProcessComponent` の編集用文字列バッファは、Drawer の .cpp 内の静的変数1組にした。Inspector に同時に表示されるのは選択中の1オブジェクトだけなので、共有で足りる。

Drawer に移す Inspector と、必要な作業（実装時の対応は表の右端）:

| 実装 | 難しさ | 必要な作業 |
| --- | --- | --- |
| `Transform::Inspector` | 易 | 不要（メンバが public） |
| `Light::Inspector` | 中 | シャドウ関連（`m_ShadowOrthoSize` / `m_ShadowFov` / `m_ShadowNear` / `m_ShadowFar`）のアクセサを追加 |
| `Camera::Inspector` | 中 | `m_Fov` / `m_Near` / `m_Far` / `m_TargetPosition` のアクセサを追加 |
| `MeshFilter::Inspector` | やや難 | ファイルダイアログ → モデル読み込み → `SetVertexData` という、まるごとエディタの処理。アクセサは揃っている。**実装では、拡張子で FBX / OBJ を判別して読み込む部分をエンジン側の処理として `MeshFilter::LoadModel()` に残し、Drawer にはファイルダイアログだけを移した** |
| `MeshRenderer::Inspector` | 難 | シェーダー選択 → PSO 再生成 → RenderManager への登録。`GetMaterial()` があるので追加は不要 |
| `FractalTreeRenderer::Inspector` | 中 | **計画書の作成後に追加された**。`MeshRenderer::Inspector()` を呼んだあと、枝のパラメータを編集する。Drawer でも MeshRenderer の Drawer を呼んでから追加分を描く形にする |
| `PostProcessComponent::Inspector` | 最難 | `m_Passes` などが private。編集用の文字列バッファを Drawer に移す。**実装では `GetPasses()` / `AddPass()` / `RemovePass()` を追加した** |
| `EditorCameraController` | — | `Inspector()` は空。`Draw()` が ImGui の入力 API を使うので、コンポーネントごと Editor に移す |

## 処理の流れと所有権

### 初期化と描画

1. 各 exe の `Main.cpp` が、ウィンドウクラスの登録とメッセージループを持つ（Editor 版と Player 版を別々に用意する）。
2. exe が `Engine::Initialize(HWND)` を呼ぶ。グローバル関数 `EngineCore::GetWindow()` は廃止する。今は Core が exe 側のグローバル変数 `g_Window` を参照していて、隠れた逆方向の依存になっている。
   **実装済み（Phase 2）**: HWND は `RenderManager` のコンストラクタと `ImGuiController::Initialize(HWND)` に引数で渡す。エディタでは、ウィンドウ作成後・表示前に `EditorApp(HWND)` を生成し（ここで描画デバイスを作る）、表示後に `EditorApp::Initialize(HWND)` で ImGui・ウィンドウ・エディタカメラ・初期シーンを準備する。従来の GameManager と同じ順序。
3. 毎フレーム `Engine::Update()` を呼んだあと、Editor は `RenderView` を2回呼んでから ImGui を描き、Player は `RenderView` を1回だけ呼ぶ。
4. メニューバー（`IDR_MENU1` / `ID_WINDOW_NEWWINDOW`）の処理は `EditorApp` が持つ。

### モジュールをまたぐときの所有権と初期化

- **シングルトン**: `ComponentFactory` / `ObjectManager` / `RenderSystem` の `GetInstance()` は、今はヘッダ内の inline 関数で実体を作っている。DLL 化すると exe と DLL で別々の実体ができてしまうので、**Phase 3 の時点で定義を .cpp に移す**（静的 lib のうちに直しても壊れないので、先にやっておける）。
- **コンポーネントの登録**: `REGISTER_COMPONENT` は static inline 変数の初期化で登録している。静的 lib にすると、誰からも参照されない .obj がリンカに捨てられ、そのコンポーネントが登録されなくなる。Phase 3 では `/WHOLEARCHIVE:EngineCore.lib` で防ぎ、Phase 6 の DLL 化で根本的に解決する。
- **Editor 側のコンポーネント**: `EditorCameraController` を Editor に移すと、Editor のコンポーネントが Core の `ComponentFactory` に登録される形になる。依存の向きは正しいので動くが、入力処理を Core 側で抽象化するまではこの形で妥協する（未決定事項 #3）。
- **メモリの確保と解放**: 確保したモジュールが解放する。`/MD`（`MultiThreadedDLL` / `MultiThreadedDebugDLL`）が全プロジェクトで揃っていることを前提にする。
- **GPU リソース（SRV ヒープ）**: ImGui は `RenderManager` の SRV ディスクリプタヒープを共有している。SceneView は `sceneViewTarget->SRVHandle.ptr` を `ImTextureID` として渡す。依存の向きは Editor から Core で正しいが、Core 側の SRV ヒープ API が Editor から見えることを確認する。

### 他の作業と並行するときのルール（提案）

分割の作業は `Split-Project` ブランチで行う（決定事項）。この作業はほぼすべてのファイルと `.vcxproj` に触れるので、他のブランチと並行するときは次を守る。

- `Split-Project` に変更を溜め込まず、**Phase ごとに master へマージする**。`Split-Project` には、こまめに master を取り込む。
- **Phase 1 の間は、既存の Inspector を触らない**。新しいコンポーネントの Inspector は、Phase 1 が master に入ってから Drawer として書く。`Inspector()` 付きで書くと、マージした後にコンパイルエラーになる。
- **Phase 1 以降、新しいコンポーネントの Inspector は `Editor/Inspector/<型名>Drawer.cpp` に書き、`REGISTER_INSPECTOR(<型名>, 関数)` で登録する**。コンポーネント側には ImGui を書かず、Drawer が使うアクセサを公開する。
- **`.vcxproj` / `.filters` はファイルを足すたびに変わる**。Phase 3 以降は、新しいファイルを `Core.vcxproj` / `Editor.vcxproj` のどちらに登録するかを、ファイルの行き先の表に従って決める。

- シェーダー（`.hlsl`）や Render 内部の作業は、Phase 1〜4 とほとんどぶつからない。

### 落とし穴

- **コンポーネントの登録が消える**: 「新しく作ったコンポーネントだけ Add Component に出てこない」という形で、分割から何週間も経ってから見つかる。Phase 3 で必ず目で確認する。
- **シングルトンが二重になる**: DLL 化した後に出る。ヘッダ内 inline のローカル static が原因になる。
- **`Core.vcxproj` の `ConfigurationType` が `Application` のまま**になっている。→ Phase 3 で解消済み。
- **相対 include が Phase 5 の移動で一斉に壊れる**: Phase 0 で先に直す。
- **`/MD` がずれる**: STL をモジュール間で受け渡した瞬間に壊れる。assimp の Debug 版誤リンクも同じ原因。
- **公開ヘッダに重いヘッダが戻ってくる**: `MeshFilter.h` を直した後も、Core の公開ヘッダを足すたびに到達するヘッダを確認し直す。1本混ざるだけで、スクリプトの再コンパイル時間が桁で変わる。
- **スクリプト DLL が静的 lib をリンクしている**: Phase 6 以降、`GameScripts.dll` の依存に `EngineCore.lib`（静的）や yaml-cpp / assimp / DirectXTex が紛れ込んでいないか確認する。
